## Ranked findings

### F1 — HOOK CONTRACT VIOLATION (crash path): hooks exit non-zero + dump an uncaught PDOException on a store/DB failure, so they are NOT actually "always exit 0 / pure observe"

- **Recommendation:** `fix` — this directly defeats the documented "write nothing to stdout and always exit 0" contract (repo-root `CLAUDE.md`, `host-agent/hooks/pre_tool_use.php:47-49`). Every hook's store write is unguarded, and every store write can throw.
- **Priority/severity:** `critical` · **Confidence:** `high`
- **Evidence:** `SqliteDb.php:68` sets `PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION`, so any SQLite failure (tmpfs `sessions_sqlite_path()` filled, WAL write locked past the 5s `busy_timeout`, schema dir uncreatable) throws. No hook catches it — I grepped the entire `host-agent/hooks/` tree for `try|catch|error_log|trigger_error` and found **zero** runtime handlers (the only "try" hits are doc-comment words). The write sites that can throw, with no guard:
  - Claude: `pre_tool_use.php:83-99`, `permission_request.php:77`, `user_prompt_submit.php:51`, `stop.php:58`, `session_start.php:139-150`.
  - Antigravity: `antigravity/pre_tool_use.php:60-70`, `antigravity/pre_invocation.php:75-86`, `antigravity/stop.php:220-233`, `antigravity/post_tool_use.php:28`.
- **Current complexity / invalid states:** For the four pure-observe Claude hooks, a throw means stderr noise + exit `255`, which Claude Code's hook runner may surface as a hook error — and for a permission-gated event the non-zero exit can be misread as a user-visible error/denial rather than a silent no-op. For the **Antigravity** hooks the failure is worse: each one has `echo json_encode(['decision' => ...])` *after* the store writes (`antigravity/pre_tool_use.php:73`, `antigravity/stop.php:235`), so a throw skips the echo entirely and Antigravity receives **no required `decision` field** → whatever the empty-stdout contract is there, it's unsatisfied. This is precisely the "failure surfaces as a crash, not a handled error" class the global CLAUDE.md test rule calls out.
- **Proposed representation:** Wrap each hook's *post-gate store work* in a `try { … } catch (\Throwable $e)` that (a) logs to a bounded file or stderr, and (b) still reaches its terminal `exit(0)` / `echo json_encode([...])`. A single tiny helper (e.g. `HostAgent\Hooks\HookSafeLog`) is the least-duplicative shape, but per-hook try/catch is acceptable given scripts are deliberately standalone. The invariant to preserve: **a CLI hook must never change its externally-observable outcome because the SQLite store threw.**
- **Smallest credible implementation scope:** add the try/catch to the 9 hook scripts (or 5 wrapper functions in a shared `host-agent/lib/hooks_common.php` that the scripts `require`, keeping each script's own body). No public interface change; store signatures unchanged.
- **Regression risks / migration concerns:** Low. Behavior on the happy path is unchanged. The only risk is over-broad `\Throwable` swallowing hiding a genuine bug — mitigate by always logging (`error_log` to `Config::sidecar_dir()/hooks.log` or stderr) and by catching `\Throwable` only around the store-write region, not the payload parse (so malformed stdin still exits 0 via the existing `exit(0)` paths, which already can't throw).
- **Validation:** The existing harness `run_status_hook_script()` (`tests/test_session_hook.php:983-1011`) captures stdout but **does not assert exit code or inspect stderr** — that's a coverage gap for this exact contract. Add a sad-path test that points `SESSIONS_SQLITE_FILE` at an unopenable path (e.g. a file path whose parent is a regular file, so `mkdir` fails) and asserts: hook exits `0`, stdout is empty (Claude) / equals the required decision (Antigravity), and the unexpected-write message appears on stderr/log. Also add an always-true assertion that `run_status_hook_script` *checks* the exit code in the first place.

### F2 — READ-MODIFY-WRITE RACE REMAINS in the SIDECAR: `session_start.php` and `antigravity/pre_invocation.php` read the sidecar in PHP then re-write the whole row

- **Recommendation:** `refactor` — this is the same race class the 2026-08-24 JSON→SQLite migration was created to eliminate (see `SessionStatusStore.php:20-25` and `SidecarStore.php:17-25`), but it still exists in the *other* store. `SidecarStore` has no atomic partial-update.
- **Priority/severity:** `high` · **Confidence:** `high`
- **Evidence:**
  - `session_start.php:83` `SidecarStore::read_sidecar($sessionName)` then `:139-150` `SidecarStore::write_sidecar($sessionName, ['workdir' => $existingSidecar['workdir'] ?? $cwd, 'spawned_at' => …, 'claude_session_id' => $claudeSessionId, 'agent' => …, 'spawned_by_csm' => …])`.
  - `antigravity/pre_invocation.php:63` `read_sidecar` then `:75-81` `write_sidecar` (same merge-with-existing pattern).
  - `SidecarStore::write_sidecar` (`SidecarStore.php:85-109`) is a full-row `INSERT … ON CONFLICT(session_name) DO UPDATE SET workdir=…, spawned_at=…, claude_session_id=…, spawned_by_csm=…, agent=…` (no `array_key_exists`-gated column subset, no `COALESCE`). So **merging against existing state requires a prior PHP read** — exactly the read-then-write gap `update_status()` eliminated.
- **Current complexity / invalid states:** A child `claude`/`agy` process spawned from inside a tracked pane inherits `CSM_SESSION_NAME` (the codebase documents this live bug class at `session_start.php:89-104` and `antigravity/pre_invocation.php:66-71`) and fires its own SessionStart / PreInvocation with its **own** conversation id. Two such firings for the same `session_name` can both read the same existing sidecar, then each write a full row; the last writer's `claude_session_id` wins, and it may be the wrong (nested/unrelated) id. The transcript-existence check (`session_start.php:105-116`) and `claude_session_id_already_live()` (`session_start.php:128-130`, `antigravity/pre_invocation.php:71`) narrow but do **not** close the window — each is itself a read-from-DB followed by a write (classic TOCTOU), and the guard read and the write are not atomic together.
- **Proposed representation:** Add `SidecarStore::update_sidecar(string $sessionName, array $fields)` that mirrors `SessionStatusStore::update_status()`: `INSERT OR IGNORE` a row, then a single `UPDATE` whose `SET` list contains exactly the keys present in `$fields` (via `array_key_exists`), preserving `workdir`/`spawned_at`/`agent`/`spawned_by_csm`/`claude_session_id` three-state semantics exactly. Then `session_start.php` and `antigravity/pre_invocation.php` call `update_sidecar` with **only** the fields they actually own (id, `spawned_by_csm` default) instead of read-merge-write. This removes the PHP-side read, which is the whole point.
- **Smallest credible implementation scope:** `SidecarStore` gains `update_sidecar()`; `session_start.php:139-150` and `antigravity/pre_invocation.php:75-81` switch to it. Keep `write_sidecar()` intact for the full-overwrite callers (`SessionLifecycleService`, etc.). `SessionService::self_heal_claude_session_id()` also does the same read-merge-write but lives in `session-view`/host-agent services — see Cross-Cutting Observations.
- **Regression risks / migration concerns:** `update_sidecar()` is additive so nothing breaks. The subtle parts to preserve exactly: `agent` defaults to `'claude'` when the key is omitted (`SidecarStore.php:107`) vs `spawned_by_csm` written as SQL `NULL` (not `0`) when the key is absent (`SidecarStore.php:106`) — a hook should pass `spawned_by_csm` only when it genuinely knows it, so `?? default` fallthrough in other callers keeps working.
- **Validation:** Existing tests cover `write_sidecar` round-trip and `prune_orphaned_sidecars`. Add a test (mirroring `tests/test_session_hook.php:454-466`) that calls `update_sidecar` twice with disjoint field sets and asserts both columns survive, plus one asserting `agent`-default and `spawned_by_csm` three-state behavior on `update_sidecar`. Add a sidecar analogue of the two-hook interleaving test.

### F3 — `update_status()` documented as an atomic `INSERT … ON CONFLICT DO UPDATE` + `COALESCE`; implemented as `INSERT OR IGNORE` + plain `UPDATE`, and not in a single transaction

- **Recommendation:** `tweak` (reconcile the docstring with reality, and optionally wrap the pair in a transaction using the repo's existing `beginTransaction` precedent) — not a bug today, but the documentation states a correctness property the code does not actually have, and a residual ordering window remains.
- **Priority/severity:** `medium` · **Confidence:** `high` (on the doc/code mismatch) · `medium` (on the ordering window's practical impact)
- **Evidence:** `SessionStatusStore.php:77-79` and the inline comment at `:94-98` describe "a single atomic UPDATE (INSERT … ON CONFLICT DO UPDATE, using SQLite's own COALESCE against the existing row)". The code is actually two statements: `:99` `INSERT OR IGNORE INTO session_status (session_name) VALUES (?)` then `:119-120` `UPDATE session_status SET status = :status, … WHERE session_name = :session_name` — a plain `SET`, **no `COALESCE` and no `ON CONFLICT DO UPDATE`**. `DETAILS.md:152` repeats the same incorrect mechanism description. By contrast the push stores that do need multi-statement atomicity use transactions: `PushSubscriptionStore.php:45-54`, `PushQuotaStateStore.php:66-85`, `PushSessionStateStore.php:47-56`.
- **Current complexity / invalid states:** The merge *is* race-free in the sense the migration cared about — because each hook only `SET`s the columns it owns, there is no PHP-side read of prior content to lose. But (a) the pair is not atomic: in autocommit a crash between `INSERT OR IGNORE` and `UPDATE` leaves a fresh all-NULL row (benign today); (b) the ordering of two concurrent same-column writers is unconstrained, so within a single tool call a **delayed** `PreToolUse` (`status='working'`, `blocked=null`, `pre_tool_use.php:99`) can land **after** that tool's own `PermissionRequest` (`status='blocked'`, `permission_request.php:62-77`), transiently turning a genuinely-blocked prompt into `working`. The docblock already names the brief optimistically-working window as "invisible to a poll-based UI" for the normal order, but it does not acknowledge the *inverted* order.
- **Proposed representation:** Update the docblock and `DETAILS.md` to say "an `INSERT OR IGNORE` to guarantee a row, then a single `UPDATE` that only touches the columns present in `$fields`" — no `COALESCE` claim. Optionally wrap the two statements in `beginTransaction()/commit()` to make "row guaranteed, then merged" a single atomic unit, matching the push-store precedent; this also lets SQLite's per-row serialization be the sole ordering authority rather than relying on two independent autocommit writes.
- **Smallest credible implementation scope:** `SessionStatusStore::update_status()` (wrap lines 98-120 in a transaction, or audit-only doc fix). No interface change.
- **Regression risks / migration concerns:** Wrapping in a transaction slightly lengthens the write-lock hold; with `busy_timeout=5000` that is fine for these micro-writes. Keep `INSERT OR IGNORE` (NOT a plain `INSERT`) so a concurrent first-writer doesn't collide.
- **Validation:** The existing merge test (`test_session_hook.php:454-466`) already covers "leaves a field it was not given untouched" and "value-null still clears (array_key_exists not isset)". Add a test that `update_status` with an explicit `'mode' => null` (which `isset` would skip but `array_key_exists` honors) still clears the column — that's the deliberate-null path the docblock calls out and is not currently directly asserted.

### F4 — `write_status()` silently drops `last_turn_error` (the column is absent from both the INSERT list and the ON CONFLICT SET)

- **Recommendation:** `fix` (latent; add the column for symmetry with `update_status`).
- **Priority/severity:** `medium` · **Confidence:** `high`
- **Evidence:** `SessionStatusStore.php:125-134` — the `INSERT` column list is `(session_name, status, blocked_json, mode, last_message, updated_at)` and the `ON CONFLICT DO UPDATE SET` mirror omits `last_turn_error` entirely; `update_status` (`:104-108`) *does* handle `last_turn_error` (it's one of the four `array_key_exists`-gated columns). `SidecarStore`/`SessionStatusStore` docs describe `write_status` as the "full overwrite" counterpart of `update_status` (`DETAILS.md:153`).
- **Current complexity / invalid states:** Every current caller of `write_status` is a test (`tests/test_session_hook.php:444,477,775,799,809`, `tests/test_sessions_lifecycle.php:1386,1395,1406,1616,1642,1656`) and **none** passes `last_turn_error`, so it is not an active bug today — but any future full-overwrite caller (or a test seeding a status row mid-debug) will silently lose the column and then wonder why `read_status` returns it as `null` while `update_status` would have preserved it. It is a trap in a shared store method.
- **Proposed representation:** Add `last_turn_error = excluded.last_turn_error` to the `ON CONFLICT DO UPDATE SET` and `last_turn_error` to the INSERT column list, and bind `:last_turn_error => $data['last_turn_error'] ?? null`. One line each.
- **Smallest credible implementation scope:** `SessionStatusStore::write_status()` only.
- **Regression risks / migration concerns:** None — existing rows are unaffected; previously-dropped values become persisted, which is the intended behavior.
- **Validation:** Extend an existing `write_status`/`read_status` round-trip test to pass `last_turn_error` and assert it round-trips.

### F5 — DRY: the gate + stdin-decode preamble is duplicated across all 9 hook scripts; Claude vs Antigravity `pre_tool_use` duplicate near-identical store logic

- **Recommendation:** `tweak` — not worth a shared base class (the scripts are deliberately standalone entry points, and the payload shapes genuinely differ: `tool_name`/`tool_input` vs `toolCall{name,args}`, and the stdout contract differs: empty vs `{"decision":"ask"}`), but the *gate* (getenv `CSM_SESSION_NAME` → no-op) + stdin `json_decode` + `is_array` preamble is copy-pasted 9× and is the highest divergence risk.
- **Priority/severity:** `low` · **Confidence:** `high`
- **Evidence:** `pre_tool_use.php:63-74`, `permission_request.php:40-51`, `user_prompt_submit.php:30-41`, `stop.php:31-42`, `session_start.php:51-57`, `antigravity/pre_tool_use.php:40-53`, `antigravity/pre_invocation.php:45-58`, `antigravity/stop.php:205-218`, `antigravity/post_tool_use.php:25-29`. Each independently re-implements "is this a CSM session?" + "decode stdin" + "is the payload an array?".
- **Current complexity / invalid states:** A future hook author is one bad copy away from forgetting the `$sessionName === ''` half of the gate (or decoding stdin before the gate and throwing on a missing `CSM_SESSION_NAME`). It's also why F1's try/catch would need 9 edits rather than 1.
- **Proposed representation:** A tiny shared helper, e.g. `HostAgent\Hooks\HookPayload::read(): ?array { $raw = stream_get_contents(STDIN); $p = json_decode((string)$raw, true); return is_array($p) ? $p : null; }` plus `HookPayload::sessionName(): ?string` (getenv gate). Each script keeps its own store-write body but calls these two — removing ~6 lines × 9 scripts of identical plumbing while preserving standalone-ness. There is no existing `host-agent/lib/hooks_common.php`; a new small file in the `HostAgent\Hooks` namespace (already PSR-4 autoloaded) is the natural home.
- **Smallest credible implementation scope:** one new small helper file + 9 `require`/call-site updates.
- **Regression risks / migration concerns:** Low — pure extraction. Keep the existing "no-op exit 0" semantics identical, including for `session_start.php`'s special handling of an absent `TMUX` env (which returns before decode in some paths).
- **Validation:** existing per-hook sad-path tests already assert the gate no-ops and malformed-payload no-ops; those tests are the safety net and must still pass unchanged after extraction.

### F6 — `SqliteDb::add_column_if_missing()` swallows *all* `PDOException`s, not just "duplicate column"

- **Recommendation:** `fix` (narrow the catch) — the "expected" case is the duplicate-column error; everything else should surface. This matters because the method runs on **every** `db()` call (`SidecarStore.php:32`, `SessionStatusStore.php:45`), so an unrelated transient error (WAL write-locked past `busy_timeout`, tmpfs full mid-ALTER) would be silently hidden just before a more confusing failure at the next statement.
- **Priority/severity:** `low` · **Confidence:** `high`
- **Evidence:** `SqliteDb.php:92-100` — `try { $pdo->exec("ALTER TABLE {$table} ADD COLUMN {$column} {$definition}"); } catch (\PDOException $e) { /* already has the column */ }` with no inspection of `$e`. The docblock (`:78-91`) itself notes the only intended swallow is the duplicate-column steady state, but the `catch` discards everything.
- **Current complexity / invalid states:** A hidden ALTER failure means a needed column silently doesn't exist, and the next real `SELECT ... last_turn_error` / `... agent` throws a confusing "no such column" from deeper code instead of the actual root cause.
- **Proposed representation:** Inspect `$e->getCode()`/message for SQLite's duplicate-column signature (`SQLSTATE`/code `HY000` with "duplicate column name") and rethrow anything else; or pre-check via `PRAGMA table_info({$table})` (cheap, once per process due to connection caching) and only ALTER when the column is genuinely absent. The latter is cleaner and avoids exception-based control flow altogether.
- **Smallest credible implementation scope:** `SqliteDb::add_column_if_missing()` only.
- **Regression risks / migration concerns:** Minimal — the steady state (column already present) still no-ops. Re-throwing on a real error surfaces it in the hook/request as `\PDOException`, which after F1's try/catch is logged rather than crashing.
- **Validation:** Existing tests cover the add-column paths indirectly (fixtures create fresh DBs). Add a test asserting the method is a no-op when the column already exists and does *not* swallow a deliberately-unrelated error (e.g. a `NOT NULL`-violating column definition on a populated table).

### F7 — Statusline quota-capture block embeds `Config::quota_live_state_write_command()` into a shell script with no quoting

- **Recommendation:** `tweak` (portability) — the block is installed into a user shell script that itself pipes to `php <path>`; the path is not shell-quoted, so a repo root (or home) containing a space breaks it. Also, the embedded path is fixed at install time, so moving the repo after install leaves a stale path (same is true of the `settings.json` hook commands, so it's a general install-time design constraint, not unique here).
- **Priority/severity:** `low` · **Confidence:** `high`
- **Evidence:** `StatuslineMarkerService.php:481` — `'  printf \'%s\' "$csm_quota_new" | ' . Config::quota_live_state_write_command() . ' >/dev/null 2>&1'`. `Config::quota_live_state_write_command()` (`Config.php:364-367`) returns `'php ' . csm_repo_root() . '/host-agent/quota_live_state_write.php'` unquoted, and `csm_repo_root()` is a real path (derived from `dirname(__DIR__,3)`, env-overridable).
- **Current complexity / invalid states:** The repo currently lives at `~/www/claude-session-manager` (no spaces) so it works today; the same embedded-path pattern is used for the hook commands, so this is consistent with the existing design rather than a regression. The session-id marker block (`:401-402`) is comparable but there `printf`/`jq` get the JSON via `$csm_statusline_input`, not a path.
- **Proposed representation:** Quote the path in the generated shell line (e.g. `printf '%s' "$csm_quota_new" | 'php' '<repo>/host-agent/quota_live_state_write.php' >/dev/null 2>&1`). Shell-quote via `escapeshellarg()` when building the block. (The hook-command strings in `Config::*_hook_command()` are a broader, cross-cutting concern — out of scope here.)
- **Smallest credible implementation scope:** `StatuslineMarkerService::append_marker_to_script()` / `quota_capture_block()` build the command line; quote it once in `quota_capture_block()` so all three install paths inherit it.
- **Regression risks / migration concerns:** `quota_capture_up_to_date()` (`:190-194`) compares the script body against `implode("\n", quota_capture_block())` — if the block text changes, a previously-installed script is seen as stale and replaced in place (that path already exists and is tested). That's the intended upgrade behavior; just be aware any `quota_capture_block()` change triggers one replace.
- **Validation:** `tests/test_statusline_marker.php` covers install/upgrade/replace and asserts quota writes reach `GlobalStateStore`. Add an assertion that the installed block contains a shell-quoted command path (or run the installed script under a repo path containing a space to confirm the regression is caught).

## What's done well

- **The atomic `update_status()` merge is correct in the way that mattered.** Each hook sets only its own columns via `array_key_exists` (not `isset`), so a deliberate `null` (Stop clearing `blocked`) still lands, and unrecognized `permission_mode` values are omitted rather than clobbering a known mode (`SessionStatusStore.php:104-114`; the omission-of-`mode` preserve test is at `test_session_hook.php:465-466`). This is genuinely immune to the lost-field read-modify-write the migration targeted.
- **The pure-observe contract is honored on the happy path** for all four Claude hooks (empty stdout, exit 0 on every gate/no-op path) and the Antigravity hooks always emit their required `decision`/`{}` shape. The CSM_SESSION_NAME gate and `AskUserQuestion` special case in `pre_tool_use.php:89-99` are well-reasoned and documented with live reproduction dates.
- **SessionStart's defense-in-depth** against the nested-`claude` clobber (transcript-existence check `:105-116`, `claude_session_id_already_live` `:128-130`) and the statusline **last-match** parsing (`StatuslineMarkerService.php:73-94`, avoiding the stale-render bug of 2026-08-23) are both genuinely careful.
- **Merge-safety is consistent** across all three installers (`HookService`, `AntigravityHookService`, `StatuslineMarkerService`): never clobber a malformed file, never clobber a user's unrelated hook, idempotent, and `StatuslineMarkerService` even distinguishes "present" from "present-and-current" for the quota block (`quota_capture_up_to_date()` `:190-194`) so a stale body is replaced rather than double-appended.
- `SidecarStore`'s `spawned_by_csm` **true/false/absent** three-state is handled with the correct `??`-fallthrough semantics and is documented with the live bug that motivated it (`SidecarStore.php:51-58,103-106`).

## Cross-Cutting Observations

- **`StatuslineMarkerService` co-ownership (per Andres's decision).** The session-id marker self-heal (parse/locate/install, `:86-306`) is this subsystem's; the quota-capture block (`QUOTA_CAPTURE_*`, `quota_capture_block()` `:474-485`, `quota_capture_installed()` `:176-194`, the replace/append paths `:355-447`, and the fallback script's quota lines `:501`) is `quota`'s target. No split proposed (none planned).
- **`SqliteDb` is shared storage infrastructure for all stores** across `sessions_schema` (this subsystem) and `push_schema` (push/quota). The transaction/atomicity and error-handling recommendations in F1/F3/F6 apply equally to the push-store side; fixing them here benefits every subsystem. The `add_column_if_missing` behavior (F6) is installed on the `sidecars`/`session_status` tables but the same helper is available to push-side stores.
- **`Config::*_hook_command()` + `csm_repo_root()`** embed an absolute repo path in `~/.claude/settings.json`, `~/.gemini/config/hooks.json`, and the statusline script. This is a deliberate install-time design (F7's quoting noted), but moving the repo means re-adding hooks — a whole-repo constraint worth a note in the coordinator's cross-subsystem report rather than per-subsystem handling.
- **The sidecar read-modify-write (F2) crosses subsystem boundaries** — it lives in the hooks (this subsystem) and is re-implemented in `SessionService::self_heal_claude_session_id()` (`session-view`). If a partial `SidecarStore::update_sidecar()` is added here, `session-view`'s self-heal should adopt it too; that's a coordination point for the `session-view` audit, not something to resolve inside this one.
